Slopsquatting: When Your AI Invents a Package and Someone Else Owns It

Published October 2026 · 7 min read

Ask an AI coding tool for a feature and it will often tell you to install something first. Usually that package is real. Sometimes it is not: the model has blended two real names, or made one up that sounds right. On its own that is harmless, because the install just fails. The problem starts when someone notices the made-up name, registers it, and puts their own code behind it. The next person who follows the same advice installs it without an error.

That attack has a name, slopsquatting, coined by Seth Larson of the Python Software Foundation. It is no longer theoretical, and it matters most to exactly the people vibe coding is for: builders who accept an install command because the AI sounded sure.

01How often AI tools invent packages

The largest measurement so far is a USENIX Security 2025 paper, “We Have a Package for You!”, by Joseph Spracklen and colleagues at the University of Texas at San Antonio, the University of Oklahoma and Virginia Tech. It won a Distinguished Paper Award. They had 16 code-generating models write 576,000 Python and JavaScript samples, which together recommended 2.23 million packages.

  • 19.7% of those packages did not exist: 440,445 hallucinations, covering 205,474 unique invented names.
  • Commercial models averaged 5.2% and open-source models 21.7%. GPT-4 Turbo was lowest at 3.59%.
  • Rates rose with the model’s temperature setting, sharply at the maximum.

Newer models are better, but not clean. A 2026 preprint by Aleksandr Churilov re-ran the test on five frontier models in April 2026 and measured rates between 4.62% (Claude Haiku 4.5) and 6.10% (GPT-5.4-mini). Its summary is the right one: the range has shrunk, the threat has not. It also found 127 invented names that all five models produced, 53 of which were still unregistered when it was written.

Around one in twenty is a small rate per suggestion and a large one per project. An app that pulls in a dozen libraries over a few weeks of prompting gets a lot of chances.

02Why repetition is what makes it an attack

If hallucinated names were random, registering them would be a lottery. They are not random. In the USENIX study, when the same prompt was run ten times, 43% of hallucinated names appeared every single time and 58% appeared more than once. An attacker does not need access to anyone’s chat. They can ask the popular models the same questions beginners ask, collect the names that keep coming back, and register them.

The invented names are also plausible by design. The researchers sorted them into conflations of two real packages (38%), near-misses of real names (13%) and pure inventions (51%). A conflation like express-mongoose looks exactly like something that should exist, which is why nobody stops to check.

That is the difference from typosquatting. Typosquatting waits for a person to mistype. Slopsquatting waits for a model to be confidently wrong in a way that repeats.

03It has already happened

  • huggingface-cli (2024). Researcher Bar Lanyado, then at Lasso Security, noticed models kept recommending pip install huggingface-cli, a package that did not exist. He registered an empty one as a test. It drew more than 30,000 real downloads in three months, and the hallucinated command had been copied into the README of a public Alibaba repository.
  • react-codeshift (January 2026). Charlie Eriksen at Aikido found this name, apparently a blend of the real jscodeshift and react-codemod, inside a batch of 47 AI-generated agent skills. Through forks it spread to 237 repositories. Nobody had registered it, so he did, defensively. It kept getting a few downloads a day, largely from AI agents following the skill’s instructions rather than from people.
  • unused-imports (npm). Models suggest this name in place of the real eslint-plugin-unused-imports. A malicious package was sitting on it and was still drawing about 233 downloads a week in early February 2026, before npm put it under a security hold.

The second case is the one to notice. The download came from an agent, not a human. As AI tools gain the ability to run install commands themselves, the moment where a person might have looked twice disappears.

04Five checks that stop it

None of these need a security background. They are the same checks a careful developer does by habit, written down because vibe coding skips the habit.

  • Look up any package you do not recognise before installing it. Open its page on npmjs.com or pypi.org. If it does not exist, the AI invented it. If it exists, check that the repository link works and points at a real project.
  • Treat a brand-new package as suspicious. A package first published last week, with one version, one maintainer and no repository, is the profile of a squatted name. The Cloud Security Alliance suggests having tools flag anything registered in the last 30 to 90 days.
  • Do not let an agent install packages unattended. If your tool can run npm install or pip install on its own, require approval for new dependencies, or keep an allowlist.
  • Commit your lockfile. package-lock.json or its equivalent pins exactly what was installed, so a later install cannot quietly pull something different.
  • Prefer fewer dependencies. Every package is a name you are trusting. If the AI wants a library to format a date or shuffle a list, ask it to write the ten lines instead.

If you are shipping something real, supply chain scanners such as Socket, Snyk or Aikido automate the first two checks and are worth the setup time.

05Where this tool stands, honestly

VibeSafe Builder narrows the problem rather than solving it, and the split is worth knowing.

Multi-file React projects: the model cannot add a package. The package.json is written by the builder, not the AI, with four fixed dependencies (React, React DOM, Vite and its React plugin). The model is told it may import only React and the project’s own files, and the in-browser preview refuses any other import with an error rather than fetching it. An invented package name has nowhere to go.

Single-file apps: these can load a library from a public CDN, and the page’s security policy only allows four CDN hosts (jsDelivr, unpkg, cdnjs and esm.sh). That stops scripts from arbitrary servers, but those CDNs serve any public npm package, including a squatted one. If the AI invents a name nobody has registered, the script fails to load and Launch Check will usually surface it as a console error or exception when it opens the app in a real browser. If someone has registered that name, nothing here checks who published it. So the advice above still applies: look at any <script src> line you do not recognise before you publish.

06The takeaway

An AI suggesting a package is not evidence that the package exists, or that the thing at that name is what the AI meant. The fix is cheap: ten seconds on the registry page before you install anything unfamiliar. The attack only works on people who skip it, and AI tools make skipping it feel normal.

07Common questions

What is slopsquatting? A supply chain attack where someone registers a package name that AI tools hallucinate, so anyone who follows the AI’s advice installs the attacker’s code.

How often do AI models invent package names? In the USENIX 2025 study, 19.7% of recommended packages did not exist (5.2% for commercial models, 21.7% for open-source). Frontier models tested in April 2026 ranged from 4.62% to 6.10%.

Is it different from typosquatting? Yes. Typosquatting relies on human typos. Slopsquatting relies on models repeating the same invented names, which makes the targets predictable.

What is the single most useful habit? Look up any unfamiliar package on its registry before installing it, and be wary of anything published very recently.
